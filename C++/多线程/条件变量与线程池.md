# 条件变量与线程池

> 一句话结论：条件变量用于在「条件不满足」时阻塞线程、条件变化时唤醒；`wait` 必须带谓词或放在循环里防虚假唤醒；线程池则是「任务队列 + 固定工作线程 + 条件变量」的标准组合。

## 为什么考 / 怎么考

条件变量是多线程面试的高频点，因为它同时考锁、等待/通知语义和竞态条件。典型追问链：

1. 为什么 `wait` 要带谓词？
2. `notify` 要不要持锁？
3. `notify_one` 和 `notify_all` 怎么选？
4. 生产者-消费者怎么实现？
5. 线程池怎么优雅退出？

## 原理

### 1. condition_variable 基本用法

`std::condition_variable` 必须与 `std::unique_lock<std::mutex>` 配合使用：

- `wait(lock)`：原子地释放锁并阻塞，被唤醒后重新加锁返回；
- `wait(lock, pred)`：等价于 `while (!pred()) wait(lock);`，是推荐写法；
- `wait_for` / `wait_until`：带超时的等待，超时返回 `std::cv_status::timeout`；
- `notify_one()`：唤醒一个等待线程；
- `notify_all()`：唤醒全部等待线程。

```cpp
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;

void producer() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        q.push(42);
    }   // 先释放锁，再通知
    cv.notify_one();
}

void consumer() {
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [] { return !q.empty(); });   // 谓词版本
    std::cout << q.front() << '\n';
    q.pop();
}
```

### 2. 虚假唤醒与丢唤醒

**虚假唤醒（spurious wakeup）**：`wait` 可能在没有 `notify` 的情况下返回。标准允许实现这样做，所以必须用谓词或 `while` 循环重新检查条件：

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

std::mutex mtx;
std::condition_variable cv;
std::queue<int> q;

void consumer_bad() {
    std::unique_lock<std::mutex> lock(mtx);
    if (q.empty()) {
        cv.wait(lock);   // 错误：没有谓词，虚假唤醒后会误以为有数据
    }
}
```

**丢唤醒（lost wakeup）**：如果在检查条件和进入 `wait` 之间，另一个线程修改了条件并 `notify`，通知会丢失。解决办法是**检查条件与 `wait` 必须在同一把锁的保护下**完成——`wait` 内部会在释放锁和阻塞之间建立原子性。

### 3. notify 要不要持锁

`notify_one/notify_all` 本身不要求持锁。常见写法是：

1. 在锁内修改共享状态；
2. 释放锁；
3. 再 `notify`。

这样可以避免被唤醒的线程立刻又因为锁被占用而阻塞。但在锁内 `notify` 也是正确的，只是可能多一次上下文切换。

注意：`notify` 不会释放锁。如果在持锁时 `notify`，被唤醒的线程会先阻塞在锁上，直到通知者离开临界区。

### 4. 生产者-消费者：有界队列

有界队列需要两个条件变量：一个表示「非空」（消费者等），一个表示「非满」（生产者等）。

```cpp
#include <condition_variable>
#include <cstddef>
#include <mutex>
#include <queue>

class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t cap) : cap_(cap) {}

    void push(int v) {
        std::unique_lock<std::mutex> lock(mtx_);
        not_full_.wait(lock, [this] { return q_.size() < cap_; });
        q_.push(v);
        not_empty_.notify_one();
    }

    int pop() {
        std::unique_lock<std::mutex> lock(mtx_);
        not_empty_.wait(lock, [this] { return !q_.empty(); });
        int v = q_.front();
        q_.pop();
        not_full_.notify_one();
        return v;
    }

private:
    std::size_t cap_;
    std::mutex mtx_;
    std::condition_variable not_full_;
    std::condition_variable not_empty_;
    std::queue<int> q_;
};
```

### 5. 线程池

线程池 = 任务队列 + 固定数量的工作线程 + 一个停止标志：

```cpp
#include <condition_variable>
#include <functional>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(std::size_t n) {
        for (std::size_t i = 0; i < n; ++i) {
            workers_.emplace_back([this] { workerLoop(); });
        }
    }

    ~ThreadPool() {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            stop_ = true;
        }
        cv_.notify_all();
        for (auto& t : workers_) {
            if (t.joinable()) t.join();
        }
    }

    void submit(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lock(mtx_);
            tasks_.push(std::move(task));
        }
        cv_.notify_one();
    }

private:
    void workerLoop() {
        for (;;) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lock(mtx_);
                cv_.wait(lock, [this] { return stop_ || !tasks_.empty(); });
                if (stop_ && tasks_.empty()) return;
                task = std::move(tasks_.front());
                tasks_.pop();
            }
            task();
        }
    }

    std::mutex mtx_;
    std::condition_variable cv_;
    std::queue<std::function<void()>> tasks_;
    std::vector<std::thread> workers_;
    bool stop_ = false;
};

int main() {
    ThreadPool pool(4);
    for (int i = 0; i < 8; ++i) {
        pool.submit([i] { std::cout << "task " << i << '\n'; });
    }
}
```

要点：

- `submit` 加锁入队，解锁后 `notify_one`；
- 工作线程用带谓词的 `wait` 等待「有任务或要停止」；
- 析构时先置 `stop_ = true`，再 `notify_all`，最后 `join` 所有线程；
- 退出策略要明确：是「处理完剩余任务再退出」（如上例），还是「立即丢弃」。

需要返回值的版本可以用 `std::packaged_task` + `std::future`：`submit` 返回 `future`，调用方 `get()` 取结果或异常。细节放到 C++11–17 新特性篇。

## 高频追问

**Q1：为什么 `wait` 要带谓词？**
A：防止虚假唤醒，同时保证被唤醒后条件仍然成立。`wait(lock, pred)` 等价于 `while (!pred()) wait(lock);`，是标准推荐写法。

**Q2：`notify` 要不要持锁？**
A：不要求。通常先修改状态、释放锁，再 `notify`；锁内 `notify` 也正确，但可能多一次唤醒后抢锁的竞争。

**Q3：`notify_one` 和 `notify_all` 怎么选？**
A：只有一个等待者能推进时用 `notify_one`（避免惊群）；状态变化影响所有等待者时（如停止标志）用 `notify_all`。

**Q4：条件变量能替代原子变量吗？**
A：不能互相替代。原子变量适合无等待的计数/标志；条件变量适合「条件不满足就睡，满足再醒」，避免忙等。两者经常一起用。

**Q5：线程池如何优雅退出？**
A：设置停止标志 → `notify_all` 唤醒所有工作线程 → `join`；同时决定剩余任务是执行完还是丢弃。不要在还有线程运行时销毁队列。

**Q6：为什么会丢唤醒？**
A：如果检查条件和进入 `wait` 不在同一把锁的保护下，另一个线程可能在这两步之间修改条件并通知，通知就丢了。锁保证「检查 + 等待」的原子性。

**Q7：`wait_for` 超时返回什么？**
A：带谓词的版本返回 `bool`（谓词是否成立）；不带谓词的版本返回 `std::cv_status`（`no_timeout` / `timeout`）。

## 易错点与加分点

- `wait` 不带谓词，虚假唤醒后直接访问空队列。
- 修改条件时不持锁，导致丢唤醒。
- 用 `if` 而不是 `while` 包裹 `wait`。
- 生产者-消费者只用一个条件变量，导致生产者/消费者互相唤醒效率低或逻辑错误。
- 线程池析构时只置标志不 `notify_all`，工作线程永远睡着。
- 被唤醒后仍持有锁做耗时操作，阻塞其他线程。
