# 线程与锁

> 一句话结论：线程的创建与回收由 `std::thread` 负责，互斥用 `mutex` + RAII 锁；`lock_guard` 最简单但不能手动解锁，`unique_lock` 更灵活，多个锁要一起加时用 `std::scoped_lock` 避免死锁。

## 为什么考 / 怎么考

多线程是中级岗位的硬门槛。面试官通常不满足于「会写 `std::thread`」，而是考锁的选择、死锁的成因与排查、以及线程生命周期管理。常见追问链：

1. `thread` 不 `join` 也不 `detach` 会怎样？
2. `lock_guard` 和 `unique_lock` 有什么区别？
3. 死锁的四个必要条件是什么？怎么避免？
4. 两个 mutex 怎么同时加锁？
5. `recursive_mutex` 为什么通常不建议用？

## 原理

### 1. std::thread 的生命周期

- 创建：传入可调用对象和参数，`std::thread t(f, args...)`。
- `join()`：等待线程结束并回收资源。
- `detach()`：分离线程，让它独立运行，资源由运行时回收。
- `joinable()`：判断线程是否仍关联一个可等待的执行体。
- **析构时仍 `joinable()` 会调用 `std::terminate`**，所以每个线程必须在析构前 `join` 或 `detach`。

```cpp
#include <iostream>
#include <thread>

void worker(int id) {
    std::cout << "worker " << id << '\n';
}

int main() {
    std::thread t1(worker, 1);
    std::thread t2([] { std::cout << "lambda thread\n"; });

    t1.join();
    t2.join();
}
```

线程函数里抛出的异常不会被主线程捕获；未捕获异常会调用 `std::terminate`。需要在线程函数内部 `try/catch`，或通过 `std::promise` / `std::future` 传递异常。

`std::jthread`（C++20）析构时自动 `join`，并通过 `stop_token` 支持协作式取消，是更安全的默认选择。

### 2. 互斥量的种类

- `std::mutex`：最基本的互斥量，不可重入。
- `std::recursive_mutex`：同一线程可重复加锁，需配对解锁。
- `std::timed_mutex`：支持 `try_lock_for` / `try_lock_until`。
- `std::shared_mutex`（C++17）：读写锁，多读单写。

### 3. RAII 锁：lock_guard、unique_lock、scoped_lock

```cpp
#include <mutex>

std::mutex m;

void withLockGuard() {
    std::lock_guard<std::mutex> lock(m);
    // 构造时加锁，作用域结束自动解锁
    // lock 不能手动 unlock
}

void withUniqueLock() {
    std::unique_lock<std::mutex> lock(m);
    // ...
    lock.unlock();   // 可以手动提前解锁
    lock.lock();     // 也可以再次加锁
}
```

- `lock_guard`：最轻量，只负责构造加锁、析构解锁，**不能手动解锁**，不可移动。
- `unique_lock`：可延迟加锁（`std::defer_lock`）、手动 `lock/unlock`、可移动，是 `condition_variable` 的必需搭档。
- `scoped_lock`（C++17）：可以同时锁多个互斥量，内部使用避免死锁的算法。

### 4. 死锁

死锁的四个必要条件：

1. 互斥：资源一次只能被一个线程占用；
2. 持有并等待：持有资源的同时等待其他资源；
3. 不可剥夺：资源不能被强行抢走；
4. 循环等待：线程之间形成等待环。

经典场景是两个线程以相反顺序加两把锁：

```cpp
#include <mutex>

std::mutex m1, m2;

void threadA() {
    std::lock_guard<std::mutex> a(m1);
    std::lock_guard<std::mutex> b(m2);   // 先 m1 后 m2
}

void threadB() {
    std::lock_guard<std::mutex> b(m2);
    std::lock_guard<std::mutex> a(m1);   // 先 m2 后 m1，可能死锁
}
```

用 `std::scoped_lock` 同时加锁，由标准库负责避免死锁：

```cpp
#include <mutex>

std::mutex m1, m2;

void fixed() {
    std::scoped_lock lock(m1, m2);   // C++17
    // 临界区
}
```

其他避免手段：

- 固定全局加锁顺序（例如按地址或 ID 排序）；
- 用 `std::try_lock` 失败后释放已持有的锁再重试；
- 缩小临界区，锁内不要调用可能再次加锁的外部代码；
- 用线程分析工具（TSan、helgrind）在测试阶段发现。

### 5. 读写锁

`std::shared_mutex` 允许多个读者并发、写者独占：

```cpp
#include <mutex>
#include <shared_mutex>

std::shared_mutex rw;
int value = 0;

int read() {
    std::shared_lock<std::shared_mutex> lock(rw);
    return value;
}

void write(int v) {
    std::unique_lock<std::shared_mutex> lock(rw);
    value = v;
}
```

读多写少的场景收益明显；写多或临界区极短时，读写锁的开销可能超过普通互斥量。

### 6. thread_local

`thread_local` 变量每个线程各有一份独立实例，生命周期与线程绑定，常用于线程本地缓存、错误码等：

```cpp
#include <iostream>

thread_local int counter = 0;

void bump() {
    ++counter;
    std::cout << counter << '\n';
}
```

## 高频追问

**Q1：`lock_guard` 和 `unique_lock` 有什么区别？**
A：`lock_guard` 只做构造加锁、析构解锁，不能手动解锁，不可移动；`unique_lock` 支持延迟加锁、手动 `lock/unlock`、可移动，并能配合条件变量。

**Q2：死锁怎么排查？**
A：用 gdb 附加后 `thread apply all bt` 看各线程卡在哪个锁；用 ThreadSanitizer（`-fsanitize=thread`）或 valgrind 的 helgrind 在测试阶段检测；生产环境结合日志和锁等待超时。

**Q3：`recursive_mutex` 为什么少用？**
A：它掩盖了「在同一线程重复进入临界区」的设计问题，容易让锁的持有范围失控；而且比普通 mutex 开销大。更好的做法是拆分函数、明确临界区边界。

**Q4：`detach()` 有什么风险？**
A：分离后无法等待线程结束，线程可能访问已经销毁的对象（悬垂引用），程序退出时也可能来不及完成；除非线程完全独立且生命周期覆盖进程，否则优先 `join` 或 `jthread`。

**Q5：两个 mutex 如何同时加锁？**
A：用 `std::scoped_lock(m1, m2)`（C++17）或 `std::lock(m1, m2)` + `std::unique_lock(..., std::adopt_lock)`，避免不同线程以相反顺序加锁。

**Q6：线程函数抛异常会怎样？**
A：未捕获异常会调用 `std::terminate`，整个进程终止。应在线程入口 `try/catch`，或通过 `future` 把异常传回主线程。

**Q7：`mutex` 和 `atomic` 怎么选？**
A：简单计数或标志位用 `atomic`，无锁、开销小；需要保护多个变量或复合操作时用 `mutex`。

## 易错点与加分点

- 创建 `thread` 后既不 `join` 也不 `detach`，析构时直接 `terminate`。
- `lock_guard` 的生命周期写成临时对象（`std::lock_guard<std::mutex>(m);`）导致立刻解锁。
- 两把锁顺序不一致造成死锁，却用「多试几次」掩盖。
- 在持锁期间调用回调或外部代码，回调里再次加锁导致死锁。
- `shared_mutex` 是 C++17 才有的；C++14 是 `shared_timed_mutex`。
- `detach` 后线程访问栈对象是典型悬垂引用。
